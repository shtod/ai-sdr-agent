## 1. 背景与目标

### 1.1 业务痛点

酷家乐 XDR 团队每天产生大量销售电话沟通记录。当前流程依赖人工从通话转写文本中提取关键信息、录入 CRM 形成 SQL（Sales Qualified Lead），存在三个突出问题：

1. **效率低**：逐条人工阅读、抽取、录入，吞吐量受限于人力；
2. **易漏判**：大量线索依赖人为主观判断，低意向与高意向难以稳定区分；
3. **准确率不稳定**：尤其是「企业抬头识别」与「客户意向度识别」两个环节，口语、简称、转写错误等因素导致结果波动大。

### 1.2 任务目标

搭建一个**可运行的 AI SDR Agent**：

- **输入**：销售电话沟通记录文本；
- **输出**：符合 SQL 字段要求的结构化 JSON 线索；
- **难点攻坚**：重点提升企业抬头识别、客户意向度识别两个环节的准确率；
- **配套工具**：针对需要人工干预的环节，设计并开发轻量级的人工干预管理工具。

### 2.3 设计原则

1. **字段规则先行**：先定义清楚 SQL 字段的抽取规则，再设计工作流；
2. **难点独立成模块**：每个难点独立成一个可解释、可替换、可单测的模块；
3. **确定性优先**：可确定计算的（评分卡加权、等级映射、字段规范化）用代码实现，不确定的（语义理解）才交给 LLM；
4. **可解释性**：每个输出都附带判断依据（`reason` / `evidence`），便于人工复核与持续调优。

## 4. Agent 工作流

流水线共 6 步（含预处理），各步骤松耦合、可独立替换。

### 步骤 0 — 预处理

- 按「销售 / 客户 / SDR / 客服 …」前缀切分话轮，无法识别说话人的行保留原文；
- 正则兜底提取手机号（真实 11 位或掩码形式）。

### 步骤 1 — 意图识别

- 用 LLM 判断是否为**有效销售线索**（`is_valid_lead`）并归类对话类型；
- 对话类型候选：`需求咨询 / 价格咨询 / 竞品对比 / 随便问问 / 售后投诉 / 无效通话`；
- **非有效线索**（如「随便问问」）强制降为 `low` 并进入人工复核，避免污染 CRM。

### 步骤 2 — 信息抽取

- LLM 抽取 `industry / area / contact_name / contact_title / phone / mendian / shejishi / demand_summary / call_time / next_action`；
- 规则：**字段缺失填 null，不编造**；手机号优先用正则结果兜底。

### 步骤 3 — 企业抬头识别（难点 1）

详见 [第 5 节](#5-难点一企业抬头识别)。

### 步骤 4 — 客户意向度识别（难点 2）

详见 [第 6 节](#6-难点二客户意向度识别)。

### 步骤 5 — 组装与复核标记

- 整体置信度 `confidence_score = min(企业抬头置信度, 意向置信度)`（短板决定）；
- `need_human_review = confidence_score < 0.7 或 企业抬头置信度 < 0.7 或 非有效销售线索`；
- 门店数 / 设计师人数尽量收敛为数字，无法提取则保留原描述；
- 附加 `_meta` 字段记录各步骤中间过程（用于工具展示与讲解）。

## 5. 难点一：企业抬头识别

### 5.1 问题定义

客户口语中常出现**简称、别称、品牌名甚至转写/ASR 错字**，需要还原出企业全称（企业抬头）。例如：

- 「木里木外」→ 可能是「木里木外家居」；
- 「索非亚」→ 「索菲亚」（同音错字）；
- 「欧排」→ 「欧派」（同音错字）。

### 5.2 三层匹配策略（由严到宽，降低误召回）

本地行业词库 `data/lexicon/company_lexicon.json` 维护「别名 → 全称」映射，召回分三层：

| 层级 | 策略 | 适用范围 | 示例 |
|---|---|---|---|
| ① 精确包含 | 原文含别名或全称 | 任意长度 | 「木里木外」直接命中 |
| ② 字符级模糊 | 编辑距离容错 | **仅 ≥3 字**候选（3~4 字容错 1 字，≥5 字容错 2 字） | 「索非亚」→「索菲亚」 |
| ③ 拼音同音匹配 | 拼音串相等（无调） | **≥2 字**候选 | 「欧排」→「欧派」 |

> **关键设计**：2 字别名**不做字符级模糊**。因为编辑距离 1 对 2 字词意味着 50% 容错，会把「我们 / 价格 / 品牌」误命中成「我乐 / 玛格 / 金牌」。2 字的错字场景改由「拼音同音匹配」覆盖，既保留容错又消除误召回。

### 5.3 大模型还原

把**候选 + 对话上下文（地区 / 行业 / 人数 / 定位）+ 词库命中结果**交给 LLM，推理还原最可能全称，输出：

```json
{
  "company_name": "索菲亚家居",
  "alias": "索非亚",
  "confidence": 0.95,
  "reason": "客户自称「索非亚」，结合定制衣柜行业与本地词库，推断为「索菲亚家居」（同音错字）。"
}
```

### 5.4 效果验证

| 测试输入 | 期望输出 | 状态 |
|---|---|---|
| 「叫木里木外」 | 木里木外家居 | ✅ 精确命中 |
| 「索非亚」 | 索菲亚家居 | ✅ 编辑距离容错 |
| 「欧排」 | 欧派 | ✅ 拼音同音 |
| 「我们做家具…价格…品牌」 | 无命中（不误召回） | ✅ 误召回防护 |

## 6. 难点二：客户意向度识别

### 6.1 问题定义

意向信号分散在对话中（预算、时间、人数、痛点、主动询问等），需要区分「高意向」与「随便问问」，并输出**等级 + 依据**。

### 6.2 评分卡设计（6 维加权，每维 0/1/2 分）

| 维度 | 权重 | 0 分（无信号） | 1 分（弱信号） | 2 分（强信号） |
|---|---|---|---|---|
| 预算 | 0.25 | 未提 | 提及价格 | 明确预算可接受 |
| 时间紧迫度 | 0.25 | 未提 | 有想法无时间 | 明确上线 / 试用时间 |
| 规模 / 人数 | 0.10 | 未提 | 模糊规模 | 明确门店数 / 设计师数 |
| 痛点明确度 | 0.15 | 未提 | 泛泛不满 | 具体业务痛点 |
| 主动询问 | 0.15 | 被动应答 | 简单追问 | 主动要方案 / 演示 |
| 决策角色 | 0.10 | 非决策人 | 中间人 | 「X 总」等决策人 |

- **LLM 先逐维打 0/1/2 分**，代码再做加权求和（确定性、可解释）；
- 总分映射：`≥1.5 → high`、`≥0.9 → medium`、否则 `low`；
- 输出逐维度证据，便于人工复核。

### 6.3 意向置信度（分类 margin）

置信度取「到最近分界线（0.9 / 1.5）的距离」：

```
margin = min(|weighted - 0.9|, |weighted - 1.5|)
confidence = clamp(0.5 + margin, 0.4, 1.0)
```

- 越靠近分界线越**不确定**（如加权 1.5 恰好卡在 high/medium 边界 → 低置信）；
- 越深入区间、或越接近两端极值（0 / 2.0）越**确定**。

> **为何这样设计**：旧公式用「到等级下限的距离」，会导致「中意向」（如加权 1.4）反而比「高意向」（加权 1.7）更自信，把本该复核的边界线索错误放行。margin 公式保证了**分界线附近必然低置信**，中意向不再被系统性高估。

### 6.4 示例

| 加权分 | 等级 | 置信度 | 是否复核 |
|---|---|---|---|
| 1.7 | high | 0.7 | 否（放行） |
| 1.55 | high | 0.55 | 是（边界） |
| 1.4 | medium | 0.6 | 是（贴近 high 边界） |
| 1.2 | medium | 0.8 | 否 |
| 0.0 | low | 1.0 | 视 is_valid_lead |

## 7. Prompt 设计

### 7.1 统一 System 角色

所有步骤共用同一系统人设，约束输出规范：

> 你是酷家乐 XDR 团队的 AI SDR Agent，负责把销售电话沟通记录（可能含口语、简称、转写错误）自动解析为结构化 SQL 线索。**只输出 JSON，不输出多余解释；字段缺失填 null，不编造。**

### 7.2 各步骤 Prompt 要点

| 步骤 | Prompt 要点 | 输出要求 |
|---|---|---|
| 意图识别 | 判断是否有效线索 + 对话类型 + 依据 | `is_valid_lead / conversation_type / reason` |
| 信息抽取 | 逐字段抽取，缺失填 null | 10 个基础字段 |
| 企业抬头还原 | 结合上下文 + 词库候选还原全称 | `company_name / alias / confidence / reason` |
| 意向评分 | 6 维分别打 0/1/2 + 证据 | `scores / evidence` |

### 7.3 工程细节

- 使用 **JSON mode**（`response_format={"type":"json_object"}`）；
- 实现**稳健解析回退**：优先解析 JSON，失败则剥离 ```json 代码块、截取首个 `{` 到末个 `}`；
- 网络 / 服务异常**指数退避重试**，重试耗尽返回 None 并由调用方降级（不中断主流程）。

## 8. 人工干预管理工具

### 8.1 定位

针对低置信度线索的**审核、修正与反馈**闭环。轻量、够用，不追求复杂。

### 8.2 页面结构（Flask 多页面 + 顶部导航）

| 页面 | 路由 | 功能 |
|---|---|---|
| 概览 | `/` | 统计卡片（全部 / 待复核 / 已修正 + 高/中/低意向分布）+ 快捷操作 |
| 录入线索 | `/add` | 粘贴通话记录 → 运行 Agent → 入库 → 就地展示结构化输出 |
| 全部线索 | `/leads` | 全部线索表格 |
| 待复核 | `/review` | 低置信度队列：并排对照原始对话与抽取结果，快速修正 |
| 反馈样本 | `/feedback` | 查看历史修正记录（标注样本） |

### 8.3 数据模型

```sql
leads (id, transcript, result, confidence, need_review, status, created_at)
corrections (id, lead_id, field, old_value, new_value, note, created_at)
```

- `leads`：存原始转写文本 + 结构化结果 + 置信度 + 复核标记 + 状态（`pending / corrected`）；
- `corrections`：每次人工修正写入（字段、旧值、新值），形成**标注样本**。

### 8.4 反馈闭环

```
低置信度线索 → 人工修正（企业抬头 / 意向等级 / 需求）→ 写入 corrections
     → 回看误判 → 迭代 Prompt / 评分卡权重 → 再次验证
```

- 支持**批量订正**意向等级；
- 修正后的线索标记为 `corrected`，退出待复核队列。

## 10. 效果验证方法

### 10.1 测试样本矩阵

| 场景 | 样本 | 验证点 |
|---|---|---|
| 高意向 + 简称 | `sample_call.txt` | 企业抬头「木里木外」→全称、意向 high |
| 转写错字 | `sample_typo_company.txt` | 「索非亚」→「索菲亚家居」 |
| 低意向 | `sample_low_intent.txt` | 「随便问问」→ low + 需复核 |

### 10.2 确定性逻辑单测

`tests/test_core.py`（`python -m pytest tests/ -v`）覆盖：词库精确 / 同音 / 错字匹配、误召回防护、手机号正则、字段规范化、意向等级映射、意向置信度 margin。

### 10.3 指标定义

- **企业抬头还原准确率** = 还原正确全称的样本数 / 总样本数（金标准人工标注）；
- **意向分级准确率** = 等级判定正确的样本数 / 总样本数（区分 high / medium / low）。

### 10.4 反馈迭代

用 `corrections` 反馈样本回看误判，迭代 Prompt 与评分卡阈值 / 权重，形成「标注 → 优化 → 验证」的持续闭环。

## 11. 工程实现要点

1. **异常处理**：LLM 调用重试 + 降级；JSON 解析多级回退；LLM 失败时字段填 null 而非崩溃；
2. **可解释性**：每个关键字段附带 `reason` / `evidence` / `_meta`，人工可复核；
3. **类型规范化**：意向等级小写收敛、布尔 / 浮点 / 数字类型统一、空串转 null；
4. **置信度校准**：分界线附近必然低置信，保证边界样本进入人工复核；
5. **可复现**：`.env.example` 提供配置模板，`requirements.txt` 固定依赖，README 说明运行步骤。

## 12. 已知局限与优化方向

| 局限 | 优化方向 |
|---|---|
| 词库规模有限 | 扩充词库 + 接入企业库 API（企查查 / 天眼查）交叉核验 |
| 无语音转写 | 引入通话录音 ASR 环节，形成端到端流水线 |
| 评分卡权重为经验值 | 用反馈样本做回归校准，边界样本二次确认策略 |
| 未接入 CRM | 接入 CRM 写回，形成完整业务闭环 |
| 单进程演示 | 生产化时替换为生产 WSGI 服务器 + 持久化数据库 |

### 13.2 运行方式

# 安装依赖

# 命令行跑通示例
